# Question Notes / leaning
Q1 Sphere radius R: a per-node starting value — independent, adjustable, user-supplied; not the length of any designated/reference edge (there is no designated edge). Resizing a node's sphere changes that node's R. RESOLVED — R is a per-node starting value, and each node's starting R = the current distance to a connected neighbor (computed from the present layout). Stored per node as data.r, adjustable thereafter (drag the sphere to resize).
Q2 Surface placement: when a node has multiple neighbors, how are they positioned on the sphere? RESOLVED — no global slot grid and no Fibonacci distribution. Initial positions seed from the present layout: each neighbor's spot = the projection of its current edge direction onto the sphere, pos = node_center + R · normalize(neighbor_current − node_center) (projectToSphere). Ongoing, dragging a node across the surface moves in steps of that node's own diameter (per-node, individual): step angle = diameter / R (diameterStepAngle), so a smaller node has finer steps / more reachable places on the same sphere, and the diameter prevents overlap. No global/Fibonacci slot scheme.
Q3 Multi-parent / multi-surface nodes: node 5 is a neighbor of both 6 and 4, so it sits on both their surfaces at once. RESOLVED — multi-surface membership is fine. Node 5 is output-less, so it owns no sphere; it is placed purely as a surface member of its connecting nodes' spheres — here both 6 and 4. Sitting on two surfaces just means it is at distance R from both, satisfiable whenever 6 and 4 are within 2R. Because the graph is under-constrained, the layout keeps them within 2R, so exact placement works. No primary-parent / midpoint rule needed.
Q4 Cycles / feedback: how does the 2 → 1 feedback edge affect the frame? RESOLVED — back edges are not excluded; all edges define the frame. The 2 → 1 edge constrains placement exactly like any other (length R, node 1 on node 2's sphere and reciprocally). There is no forward-only traversal / spanning tree; the whole edge set is the frame.
Q5 Position computation & interaction: how are world positions computed, and what does dragging/resizing do? RESOLVED — positions are computed by propagation from an anchor node (default node 1; or the last-resized node) over the connection graph: each neighbor is placed by projecting its current edge direction onto the placing node's sphere (placing_node_center + R_placing · normalize(neighbor_current − placing_node_center)). Back edges to already-placed nodes don't re-place them. Output-less nodes (3, 5) are placed as surface members on their first connecting node (multi-surface ok). Resizing a node's R re-anchors propagation at that node, so the rest of the connected structure flexes/moves (the "not rooted" behavior). Dragging a neighbor moves it across the surface in steps of its own diameter; resizing drags the surface to change R.
Q6 Output-less / dangling nodes: node 3's dangling output and the sink node 5. RESOLVED — output-less nodes have no sphere of their own; they are surface-only, placed solely as surface members of the node(s) that connect to them (possibly several — node 5 on both 6 and 4). This is a local, per-node frame, not a rooted traversal of the whole graph.
Q7 Storage: the lattice stored (i,j,k) per node. Sphere-chain positions are derived from the graph — is anything stored per node (e.g. the chosen dir / angle on the parent sphere, so it's stable across loads), or fully recomputed each load? RESOLVED — per node, data.r (the node's R) and each neighbor's surface direction (its dir on the sphere, as last dragged) are stored; world positions are recomputed each load by propagation from the anchor, with initial directions seeded by edge projection. Geometry is Go-owned: Go computes + streams positions, TS renders.
