The big open question: with positions derived from the topology, what happens to node dragging? Two framings:

A — Auto-computed (no dragging)

The layout is fully a function of the graph. Because the topology is sparse, Go can compute an exact uniform-R placement deterministically (no relaxation); the user never moves nodes by hand. Changing the layout means changing the wiring (or the layout parameters), not dragging.

B — Draggable on the sphere

Nodes remain movable, but constrained to the model: e.g. a child slides around on its parent's sphere surface (changing its dir at fixed R) in steps of its own diameter (step angle diameter / R), so a smaller node has finer steps; the tree can be re-rooted. Dragging adjusts dir/angle rather than free-placing.

Which framing wins is open (Q5). Either way, the lattice's drag-snap-to-cell behavior is gone — there are no cells to snap to.

First-cut visualization (committed 837087f7)

A "sphere" button toggles a see-through torus ring at radius R for the selected node (styled like that node's border torus). It shows the node's own sphere. R there currently uses the live primary-output-edge distance as a stand-in for the node's starting R value (the real per-node starting value is still Q1). Neighbors are seeded on the surface by projecting their current edge direction onto it and thereafter drag across the surface in steps of the dragged node's own diameter; dragging the surface inward shrinks that node's R.
