Model

Sequences are the top level of the step tree. A step can hold steps, and the scene holds sequences in the same way. Nodes are not part of this hierarchy. Which node set a sequence uses is a storage fact, not something the tree shows.

The dashed line is the one visible cost. Moving within a sequence is in-process: the nodes call loadGrid(level), at Categories/NodeKinds/PhiTheta/grid.go:82. Moving to another sequence rewrites view/sequence.bin and reloads the network, at Categories/Scene/Dispatch/sheet_structure.go:148. In the tree both are a single click.

What it reverses

  • Navigating by descent. Today you see one level at a time, enter a child with “Go inside” and climb back with the trail. After, every level stays visible at once, and where you are is the highlighted row, not a breadcrumb.
  • Sequences as a separate place. Today sequences have their own page (AtSeqs) and a crumb menu. After, they are the tree’s top rows. Add, duplicate, delete and rename move into each sequence row’s menu.
  • The step chip bar as the step list. stepBar shows only the current level, as a flat list. After, the tree is the step list. The “showing step N” status line stays.
The step columns (the score) and the inspector do not change. The tree only chooses which level and step they show.

On disk: no change

The tree reads the layout that exists today. A sequence folder and a nested level hold the same parts (nodes/, steps/), so the reader can walk them with one recursive function.

Order

One commit per step, each with stop-checks clean and driven in the editor before the next.

  1. Rows. step_tree.go builds the rows, and a temporary breadcrumb prints their count so the walk can be checked against find sequences -path '*steps*'.
  2. Draw it beside what exists. The tree pane shows up with every old navigator still in place. Clicks do nothing yet.
  3. tree-go within a sequence. Clicking a row in the open sequence changes level and step. The chips and trail still work, so the two can be compared directly.
  4. tree-go across sequences. Persist the level and step through the reload. Clicking a step inside another sequence lands on that step, not on that sequence’s top level.
  5. Row menus. Sequence rows get add, duplicate, delete and rename. Step rows get the existing step tools plus “Add inner step”. Add the filter field.
  6. Remove the old navigators. Everything marked “gone” above goes in one commit, so there is never a state with two ways that disagree.
  7. Narrow width. Fold the tree into the chip-and-popover form below narrowW.

Verification

There are no tests. Verification is driving the editor on topology-phi-theta, which already has nested levels in sequences 1 and 8.

  • The tree shows sequences 1–11, and sequences 1 and 8 expand two levels deep. The numbers match the folders on disk.
  • From sequence 10, step 1, click sequence 8 › step 1 › step 1. The diagram reloads, the inner step is highlighted, and the columns show that level.
  • Add an inner step to a step that has none. steps/n/steps/1 appears, and the row gets a twisty.
  • Delete the open sequence. The tree highlights a neighbour, and nothing refuses or panics in .probe/go-errors.log.
  • Make the panel narrow. The tree becomes the chip, and choosing a row from its popover works the same.
  • grep -rn 'OpStepEnter\|AtSeqs\|stepBar' Categories is empty after step 6.

Risks

  1. The level is lost on reload. Model.Level is memory only, and a sequence switch rebuilds the network. Step 4 has to write it somewhere the reload reads, such as the open sequence’s view/. Otherwise a cross-sequence click lands on the top level.
  2. Width. The Links tab already splits into columns and an inspector. A third pane squeezes the columns. The tree needs a hard cap (around 200px) and the narrow-width fold.
  3. Walking the disk on every redraw. Eleven sequences, each a few levels deep, is cheap, but the rows should be rebuilt on structure ops and reloads only, like LoadSequences, not on every layout.
  4. The 200-line file ceiling. pill_sequences.go (169) and links_score.go (189) are near the limit. The tree lives in new files, and moving the row menus may mean splitting what is left.
  5. Empty steps/ folders. A “Go inside” that was never filled leaves a level with no steps. The tree should hide the twisty when there are no step folders, not when the folder is missing.

Open questions

  • Where should fold state live? The proposal is per level, beside open.bin, so it survives reloads the same way step-card open state does.
  • What does clicking a sequence row show: its step 1, or the step that was last shown in it? The proposal is the last shown step, which needs the same storage as risk 1.
  • Should a row be draggable to reorder or reparent? Not in this plan. “Move earlier” and “Move later” stay as menu items.
