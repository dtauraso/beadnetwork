The whole case space

A node's tilt machine is ONE instance (tiltMachine) whose entire state is which mode it is in. So the cases are: three modes, each against every COUNT an arrival can produce — the ring slots between the arrival and the NEARER END of this node's tilt line (nearerEndCount). A node draws two ends a half turn apart, so exactly one count is under a half turn, and that is the one. The grid runs 0 to 11 on a 24-point ring, not 0 to 12: c lives on a ring of a HALF TURN, and 12 is 0 at the other end. Nothing else is a case: the turn never sees which mode is running, and there is no fourth input.

Read a row and you have that mode entirely. SETTING stops at every count, which is why a node being set up cannot be moved by an arrival. The other two stop at ONE count each and turn straight over the other's — perpendicular walks through a quarter turn, parallel walks through 0. Each row is a single run of ‹ and a single run of ›, because the rule is a single comparison: is the stop within a quarter turn going up.

The two ties, and which way they break

case why it is a tie what happens
perpendicular, c = a quarter turn its stop, 0, is a quarter turn away going either way round the count-ring turns UP
parallel, c = 0 its stop, a quarter turn, is a quarter away going either way round turns UP
Both fall out of one <= in step: the way up is measured against a quarter turn, and at exactly a quarter the two ways round are the same length, so the ≤ takes it up. It is a convention, not a measurement — there is no better answer, since the two directions are genuinely the same distance. What matters is that it MOVES: standing still at a tie is the freeze the old "not acute" test produced. There are TWO ties and not four: read from the nearer end, each mode has one stop, so each has one count that sits opposite it.

Every transition — there are four, and no others

from → to what causes it source
setting → perpendicular first arrival, and the gap between the two TILTS is a quarter turn machineForGap

setting → either the partner already chose and its reply carries the choice adoptMachine
perpendicular or parallel → setting RESET, and nothing else clear
There is NO perpendicular ↔ parallel edge. A chosen mode STICKS: a second choice — a click landing mid-run, or the partner's own answer arriving after this end already decided — is ignored, because re-deciding on a jitter is what once switched a started perpendicular pair to parallel one step after START.

What the gap read actually asks

arrival lands at count the two tilts are mode chosen
c = 0 — on this node's tilt line, either end a quarter turn apart — ALREADY perpendicular. The code measures this the other way about, as the gap between the two TILTS being a quarter turn (machineForGap); the two are the same fact, since the arrival is the partner's normal perpendicular
anything else an acute gap parallel
The two rows are perpendicular's gap and everything else, which is the honest reading of the rule: it asks "is this setup already perpendicular?", and everything that is not becomes a parallel pair to be closed. A pair set up at a quarter turn is therefore perpendicular and finished on arrival — it has nowhere to walk.
